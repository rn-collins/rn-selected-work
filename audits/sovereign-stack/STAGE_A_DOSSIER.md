## 2. Executive verdict

This is one of the stronger proposal artifacts in the estate. It makes governance concrete without pretending that a form creates consent or authority. Its refusal paths, knowledge-class boundaries, explicit unresolved states, staged discovery/pilot/production gates, local-only draft handling, source-category register and repeated non-affiliation language are unusually responsible. The public-source claims about Purple Maiʻa's local cluster, edge processing, KILO, data sovereignty and Kula are substantially supported by Purple Maiʻa's own current pages.

It remains a **proposal generator**, not a governance system. All roles, approvals, signatures, visibility classes, records and readiness determinations are browser simulations. Identity, standing, access, server authorization, retention, deletion, version integrity, audit history, publication approval and migration are not implemented. Local storage is neither secure nor an organizational record. Downloads are unsigned JSON/Markdown created entirely on the client.

The largest substantive risk is ownership/relationship language. “A Purple Maiʻa-owned way,” “Purple Maiʻa would own,” “Purple Maiʻa has already built the technical embodiment,” “has built sovereign technical capacity,” and social metadata promising a “Purple Maiʻa-owned” layer can be read as present fact, transfer, adoption or relationship. The proposal itself correctly says actual ownership needs a contract and that the organization may reject the premise; the hero, meeting copy, metadata and portfolio synopsis must preserve that conditionality.

**Release recommendation:** retain as P because it is the canonical, distinct consumer artifact already represented in the portfolio, but label it a live browser-local independent proposal and hold broader promotion until claim, ownership, storage-copy, build-pipeline and accessibility corrections are complete.

## 7. Copy and information-architecture findings

Strengths include the public-fact/interpretation/proposal/unresolved separation; conspicuous non-affiliation language; “stop is successful”; narrow discovery-to-pilot-to-production sequence; plain warnings against protected data; and unusually truthful download caveats.

6. The privacy dialog says entries are not transmitted “by this application”; clarify that ordinary hosting/CDN request metadata still reaches Vercel and network providers, even without analytics or draft transmission.
7. Add version/as-of dates next to each source and a correction/contact route.
8. Replace personal “CEO/Donavan” labels on a public portfolio artifact unless public tailoring is authorized.

## 12. Security, privacy, data and operations

- Drafts use `localStorage` key `sovereign-stack-demo-record`; stored fields include system record, project name, visibility, owner, review date, decision text, snapshots/logs, production records, session and charter. Gate answers/notes/purpose and executive-review notes are not persisted.
- Local storage is readable by same-origin script, unencrypted, device/profile dependent, unsynchronized and not suitable for protected/confidential records. Erasure removes the key but cannot prove browser/device backups, screenshots or downloaded copies are gone.
- Downloads are unsigned client-created Markdown/JSON. They lack identity verification, authority proof, record hashes, access controls, watermarking enforcement, revocation and audit trail.
- No application API, database, accounts, cookies or configured analytics were found. Hosting necessarily processes ordinary request metadata; the privacy copy should not imply zero third-party processing.
- No explicit CSP, frame-ancestors/X-Frame-Options, nosniff, referrer or permissions policy is configured in repository files. HSTS was observed at Vercel; root responded with permissive `Access-Control-Allow-Origin: *`, which is low impact for public static content but should not be inherited by future protected APIs.
- Manifest operations are inconsistent: Vercel uses `npx next build`, bypassing the missing custom validation pipeline. Local `build`, `test`, `lint`, `dev` and `start` cannot be certified from current repository contents. Mixed Next/Vinext/Vite/Wrangler/Drizzle dependencies are unexplained and expand supply-chain/maintenance surface.
- The current `app/page.tsx` blob SHA differs from the deployment-linked commit metadata observed in the estate, and that deployment commit was not fetchable through the connector. Reconcile source-to-deployment provenance before claiming the live artifact is current.
